Subject goals

The course gives you a working knowledge of:

  • the basics of control engineering and control theory;
  • the dynamic behavior of a vehicle — and of the driver as a controller;
  • the car's communication bus;
  • electric cars and their components: DC machines, asynchronous and synchronous motors — principles, construction, basic properties and operation;
  • hybrid drive systems;
  • the car's control, safety, communication and comfort electronics.

Say: a car today is a set of systems that talk to each other — engine, brakes, steering, batteries, comfort — and most of them are controlled by software. This course goes through those systems one at a time: what each does, the physics behind it, and how it is controlled.

Point at: the driver as a controller. The driver is part of the loop too: they watch the speed and press the pedal. Many systems in the course either help the driver (cruise control, ABS) or replace them.

How a lecture and a practical work

A typical lecture

  1. Introduction — purpose and functions of the system.
  2. The physics behind it.
  3. Its main components.
  4. Its algorithms and control strategy.

A typical practical

  1. A short reminder of the theory.
  2. Building the model — guided, step by step.
  3. "Playing" with the model to reach the task's goal.
  4. A short report at home, about half a page to one page.

Say: lectures go from "what is it for" down to "how is it controlled". Practicals turn that into a model you build and experiment with. The report is short on purpose: what you tried, what you saw, what it means.

The tool: Dyad

All modeling in this course is done in Dyad, by JuliaHub: you draw or write a model of a physical system, and it simulates it. Together we build one library of vehicle components and test different vehicle systems on it.

Focus: the car's 1D (longitudinal) motion.

Components

engine · electric motor · wheels · transmission · brakes · driver

Systems we simulate on them

ABS, ESP and TCS · electric drive and its control · hybrid architecture · adaptive cruise control

Documentation: help.juliahub.com/dyad/dev

First practical: build the car in Dyad.

Say: one tool for the modeling practicals. Dyad is a modeling language and a VS Code extension: you place components like engine, gear and wheel, connect them, and simulate. Underneath it is Julia, but you will mostly draw and write models, not program.

Point at: the screenshot. Every block in the diagram is a line of code on the right, and every wire is a connect. You can work in either view.

Say: we stay in one dimension — the car moving forward and back. That is enough for the engine, the drivetrain, braking, traction and cruise control, and it keeps the models small enough to understand completely. The autonomous-vehicle practical is the exception: it uses the CARLA simulator.

Say: lectures and practicals alternate, and every practical builds on the lecture before it — in Dyad, in your own repository, in the same vehicle library.

Walk the flow: first you build the car (3). Then its powertrain, one kind at a time: the combustion engine (4–5), then the electric motor with its controller and a hybrid drive that combines the two (6–8), and fuel cells as the next source of electric power (9). With the drive done, the safety systems that act on it (10–11): ABS stops the wheels locking when braking, TCS stops them spinning when accelerating, ESP keeps the car from sliding sideways. Comfort and assistance systems (12) and autonomy (14) close the course. The autonomy practical leaves Dyad: in the CARLA simulator you work with the car's camera and sensors in a virtual city.

Abbreviations: ABS — anti-lock braking system. ESP — electronic stability program. TCS — traction control system.

Say: the email in git config is what links each commit to your GitHub account. If it does not match, your commits show up without your name.

How Git works

  • Repository — a folder whose history Git keeps.
  • Commit — a saved snapshot of the files, with a message saying what changed. You can always go back to one.
  • Branch — a line of commits. main is the accepted version; you work on your own branch.
  • Remote — the copy on GitHub. Push uploads your commits, pull downloads others'.

Say: Git is a save system with memory. Every commit is a snapshot you can return to, so you can try something risky in a model and undo it.

Walk the picture: you edit files; git add picks which changes go into the next snapshot; git commit saves it on your machine; git push sends it to GitHub. git pull brings changes from GitHub back — anything changed there since your last pull.

Say: nothing reaches GitHub until you push. A commit on your laptop only is not handed in.
